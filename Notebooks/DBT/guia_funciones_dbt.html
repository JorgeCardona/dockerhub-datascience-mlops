  • Origen de scripts: Lee todos los modelos .sql de la carpeta models/.

1. Conceptos Fundamentales de dbt (Antes de ver el código)

¿Qué es un Modelo? (.sql)

Un modelo es simplemente un archivo de texto con extensión .sql guardado dentro de la carpeta models/ de tu computadora.

Contiene una única consulta SELECT. dbt se encarga de envolver ese SELECT dentro de un CREATE TABLE AS o CREATE VIEW AS en tu base de datos.

-- Archivo: models/stg_clientes.sql
SELECT
  id AS cliente_id, -- INT
  TRIM(full_name) AS nombre, -- VARCHAR
  status AS estado -- VARCHAR (Valores: activo, inactivo)
FROM prod_dw.raw_salesforce.sf_users
-- Ejemplo adicional uniendo source() y ref():
SELECT
  c.cliente_id,
  c.nombre,
  p.nombre_pais
FROM {{ source('crm', 'clientes') }} c
LEFT JOIN {{ ref('codigos_pais') }} p ON c.pais_id = p.id

¿Qué es una Materialización?

Es la forma física en que dbt guarda el resultado de tu modelo .sql dentro del Data Warehouse:

• View (Vista): Guarda solo la consulta virtual.
• Table (Tabla): Crea una tabla física completa cada vez.
• Incremental: Crea la tabla la primera vez y luego solo inserta filas nuevas.

-- Archivo: models/fct_ventas.sql
{{ config(materialized='table') }}

SELECT
  id_venta, -- INT
  monto, -- FLOAT
  fecha -- DATE
FROM raw_ventas

¿Qué es un Seed? (.csv)

Un seed es un archivo estático en formato .csv (como un catálogo de países, monedas o metas) guardado en la carpeta seeds/.

Al ejecutar dbt seed, dbt lee ese CSV de tu disco y crea una tabla real con sus datos dentro de la base de datos.

-- Archivo: seeds/codigos_pais.csv
id,nombre_pais,moneda
CO,Colombia,COP -- VARCHAR
MX,Mexico,MXN -- VARCHAR

¿Qué es un Source? (.yml + .sql)

Son las tablas crudas (raw) que ya existen en tu base de datos porque las cargó otra herramienta (Fivetran, Airbyte, Python).

Como dbt no las creó, debes declararlas en un archivo sources.yml especificando sus columnas, tipos de datos y reglas, para luego consultarlas mediante source().

-- Archivo: models/sources.yml
version: 2
sources:
  - name: crm # Alias del sistema
    tables:
      - name: clientes # Alias dbt
        identifier: sf_users # Tabla real
        columns:
          - name: id -- INT (Único)
          - name: status -- VARCHAR (Valores: activo, inactivo)
-- Uso en models/stg_clientes.sql
SELECT id, status FROM {{ source('crm', 'clientes') }}

¿Qué es ref()? (Función Jinja)

ref() es la función principal de dbt para conectar modelos entre sí. Toma el nombre de otro modelo o seed sin extensión y resuelve automáticamente su ruta física en el Data Warehouse.

Garantiza que dbt construya el DAG (linaje) ejecutando primero los modelos dependientes.

-- Archivo: models/dim_clientes.sql
SELECT
  c.cliente_id,
  c.nombre,
  p.nombre_pais -- VARCHAR
FROM {{ ref('stg_clientes') }} c
LEFT JOIN {{ ref('codigos_pais') }} p ON c.pais_id = p.id

¿Qué es un Test? (Prueba de Calidad)

Los tests en dbt son aserciones sobre tus datos para garantizar la calidad (ej. verificar que una columna sea única, no nula, o cumpla relaciones).

Se definen principalmente en archivos .yml adjuntos a tus modelos.

-- Archivo: models/schema.yml
version: 2
models:
  - name: dim_clientes
    columns:
      - name: cliente_id -- INT
        tests: [unique, not_null]
      - name: estado -- VARCHAR
        tests: [{accepted_values: {values: ['activo', 'inactivo']}}]

¿Qué es el DAG (Linaje)?

Es el mapa de dependencias que dbt arma automáticamente al leer tus source() y ref().

Si el modelo B tiene {{ ref('modelo_a') }}, dbt sabe que primero debe construir modelo_a en la base de datos antes de ejecutar modelo_b.

-- Orden de ejecución del DAG en consola:
1. source('crm', 'clientes') ➔
2. models/stg_clientes.sql ➔
3. seeds/codigos_pais.csv ➔
4. models/dim_clientes.sql

¿Qué es profiles.yml?

Es el archivo de configuración de conexión (fuera del repositorio del proyecto) donde defines a qué base de datos conectarte y en qué esquema trabajar.

Por ejemplo, define que en entorno dev escriba en dev_juan y en prod escriba en prod_dw.analytics.

-- Archivo: ~/.dbt/profiles.yml
mi_proyecto:
  target: dev -- Entorno activo
  outputs:
    dev:
      type: snowflake
      database: dev_dw -- VARCHAR
      schema: dev_juan -- VARCHAR

2. La Duda Clave: Si stg_clientes.sql es un archivo local, ¿por qué {{ ref('stg_clientes') }} consulta prod_dw.analytics.stg_clientes?

dbt nunca ejecuta consultas SQL contra archivos de texto en tu disco duro. dbt es un orquestador y compilador que trabaja siempre contra tu Data Warehouse (Snowflake, BigQuery, Postgres, etc.). El ciclo funciona en 3 pasos exactos:

Paso 1: Orden de ejecución Al ver {{ ref('stg_clientes') }} dentro de dim_clientes.sql, dbt detecta una dependencia y ejecuta primero el archivo models/stg_clientes.sql.
Paso 2: Creación en la BD dbt toma el SELECT de stg_clientes.sql y crea una tabla o vista real en tu Data Warehouse llamada prod_dw.analytics.stg_clientes (usando la base de datos y esquema configurados en tu profiles.yml).
Paso 3: Traducción del ref() Ahora que la tabla física ya existe en la BD, dbt reemplaza el texto {{ ref('stg_clientes') }} por la ruta real de esa tabla en la BD: prod_dw.analytics.stg_clientes.

source() .YML
models/sources.yml
  • En un archivo .yml defines un alias de sistema (crm) y un alias de tabla (clientes).
  • Ese YAML actúa como un diccionario que mapea tus alias hacia la base de datos, el schema y el nombre físico real (identifier) de una tabla externa que ya existe en el Data Warehouse.
 Exclusivamente en los primeros modelos (capa staging) para leer tablas crudas cargadas por herramientas externas (Fivetran, Airbyte, etc.).
1. Diccionario en models/sources.yml.YML
version: 2 sources: - name: crm # Alias del sistema (inventado por ti) database: prod_dw # Base de datos real en tu servidor schema: raw_salesforce # Esquema real donde cae la ingesta tables: - name: clientes # Alias de la tabla en dbt identifier: sf_users # Nombre físico real de la tabla

SELECT id AS cliente_id, TRIM(full_name) AS nombre, country_code AS pais_id FROM {{ source('crm', 'clientes') }}

.CSV
  • No usa YAML. Toma el nombre exacto del archivo físico (.sql o .csv) sin su extensión.
  • Primero dbt materializa esos archivos como tablas/vistas reales en el esquema de destino configurado en profiles.yml (ej. prod_dw.analytics), y luego reemplaza ref() por esa ruta de base de datos.
 En todos los modelos intermedios y finales (marts) para cruzar datos que ya pasaron por otro modelo o seed dentro de dbt.

-- dbt crea la vista/tabla prod_dw.analytics.stg_clientes con esto: SELECT id AS cliente_id, TRIM(full_name) AS nombre, country_code AS pais_id FROM prod_dw.raw_salesforce.sf_users
1B. Archivo previo seeds/codigos_pais.csv.CSV
-- Al correr "dbt seed", dbt sube estas filas a prod_dw.analytics.codigos_pais: id,nombre_pais CO,Colombia MX,Mexico

config() .SQL
.YML
  • Define cómo dbt debe construir físicamente el modelo en la base de datos (table, view, incremental o ephemeral).
  • Se escribe en la cabecera del propio archivo .sql (y tiene prioridad sobre lo que diga dbt_project.yml).
 Al inicio de un archivo .sql cuando quieres que ese modelo específico se guarde como tabla física o incremental en lugar de una simple vista.
1. Cabecera en models/fct_ventas.sql.SQL
{{ config( materialized='table', tags=['finanzas', 'diario'] ) }} SELECT id_venta, monto, fecha FROM {{ ref('stg_ventas') }}
2. Acción que dbt ejecuta en la BDEJECUCIÓN
CREATE OR REPLACE TABLE prod_dw.analytics.fct_ventas AS ( SELECT id_venta, monto, fecha FROM prod_dw.analytics.stg_ventas );
is_incremental() .SQL
  • Función booleana (True / False) nativa dentro de un archivo .sql.
  • Devuelve True únicamente si se cumplen 3 condiciones: el modelo tiene materialized='incremental', la tabla ya existe en la BD y no pasaste el comando --full-refresh.
 Dentro de un bloque {% if %} en tablas históricas muy grandes para procesar solo los datos nuevos del día y evitar reprocesar millones de filas viejas.
1. Modelo models/fct_eventos.sql.SQL
{{ config(materialized='incremental') }} SELECT id_evento, fecha_hora, usuario_id FROM {{ ref('stg_eventos') }} {% if is_incremental() %} WHERE fecha_hora > (SELECT MAX(fecha_hora) FROM {{ this }}) {% endif %}
2. SQL compilado (2da ejecución en adelante)COMPILADO
INSERT INTO prod_dw.analytics.fct_eventos SELECT id_evento, fecha_hora, usuario_id FROM prod_dw.analytics.stg_eventos WHERE fecha_hora > (SELECT MAX(fecha_hora) FROM prod_dw.analytics.fct_eventos)
this .SQL
  • Variable automática que representa el nombre completo en la base de datos del mismo archivo .sql que se está ejecutando en ese instante.
  • Evita que tengas que escribir a mano el nombre de la tabla actual y permite que funcione tanto en dev como en prod.
 Junto al uso de is_incremental() para consultar cuál fue la última fecha o ID guardado en la versión existente de esa misma tabla.

Terminal / Servidor
  • Lee una variable de entorno almacenada en la memoria del sistema operativo donde se ejecuta dbt (Linux, Windows, Docker, GitHub Actions).
 Para inyectar contraseñas, tokens de acceso o nombres de bases de datos sin escribir credenciales reales dentro de los archivos del proyecto Git.
1. Variable en Terminal / Servidor CIOS
export DBT_PROD_PASSWORD="ClaveSuperSecreta99"

outputs: prod: user: dbt_service_user password: "{{ env_var('DBT_PROD_PASSWORD') }}"
execute .SQL
  • Bandera interna de dbt. Vale False durante la fase 1 (cuando dbt lee archivos para armar el DAG) y cambia a True en la fase 2 (cuando ya está conectado ejecutando SQL real).
 Obligatoriamente alrededor de funciones como run_query() para evitar que dbt falle durante la lectura inicial de archivos.
1. Protección en models/pivot_pagos.sql.SQL
{% if execute %} {% set resultados = run_query("SELECT DISTINCT tipo FROM pagos") %} {% set lista_tipos = resultados.columns[0].values() %} {% else %} {% set lista_tipos = [] %} {% endif %}
run_query() .SQL
  • Envía una consulta SQL escrita por ti hacia la base de datos antes de compilar el modelo y guarda los resultados en una tabla en memoria Jinja (Agate Table).
 Para construir consultas SQL dinámicas (como un PIVOT automático de columnas) basándote en los valores reales que existen en una tabla.
1. Código dinámico en models/resumen_pagos.sql.SQL
{% set q = "SELECT DISTINCT metodo FROM prod_dw.analytics.stg_pagos" %} {% set metodos = run_query(q).columns[0].values() if execute else [] %} SELECT cliente_id {% for m in metodos %} , SUM(CASE WHEN metodo = '{{ m }}' THEN monto ELSE 0 END) AS total_{{ m }} {% endfor %} FROM {{ ref('stg_pagos') }} GROUP BY 1
2. SQL compilado si la BD devolvió ['tarjeta', 'efectivo']COMPILADO
SELECT cliente_id , SUM(CASE WHEN metodo = 'tarjeta' THEN monto ELSE 0 END) AS total_tarjeta , SUM(CASE WHEN metodo = 'efectivo' THEN monto ELSE 0 END) AS total_efectivo FROM prod_dw.analytics.stg_pagos GROUP BY 1
adapter .SQL

 Para asegurar la integridad de un modelo específico antes de entregar datos a negocio.
Opción A: Test genérico para un solo modelo (models/schema.yml).YML
version: 2 models: - name: dim_clientes columns: - name: cliente_id tests: - unique - not_null
Query de auditoría que dbt compila y ejecuta para este modeloCOMPILADO
SELECT cliente_id FROM prod_dw.analytics.dim_clientes WHERE cliente_id IS NULL OR cliente_id NOT IN ( SELECT cliente_id FROM prod_dw.analytics.dim_clientes GROUP BY 1 HAVING COUNT(*) = 1 );

-- Valida una regla específica: este modelo jamás debe tener clientes sin estado activo SELECT cliente_id FROM {{ ref('dim_clientes') }} WHERE estado != 'activo'

SELECT cliente_id FROM prod_dw.analytics.dim_clientes WHERE estado != 'active';

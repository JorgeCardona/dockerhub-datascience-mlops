Super Guía de dbt: Arquitectura, Conceptos y Funciones

Entiende desde cero cómo dbt conecta tus archivos locales (.sql, .csv, .yml) con las tablas reales de tu Data Warehouse y domina todas sus funciones Jinja con ejemplos completos de extremo a extremo.

1. Conceptos Fundamentales de dbt (Antes de ver el código)

1.1 Fundamentos y Anatomía de Macros en dbt

¿Qué es una Macro? (macros/*.sql)

Una macro es una función escrita en Jinja que vive en un archivo .sql dentro de la carpeta macros/. Recibe argumentos y devuelve texto (normalmente un trozo de SQL) que dbt pega exactamente donde la llamaste.

Equivale a una función de Python: la defines una vez y la llamas desde cualquier modelo, test, hook o desde la terminal.

-- Archivo: macros/limpiar_texto.sql {% macro limpiar_texto(columna) %} UPPER(TRIM({{ columna }})) {% endmacro %} -- Uso: SELECT {{ limpiar_texto('nombre') }} ... -- Resultado: SELECT UPPER(TRIM(nombre)) ...

Anatomía de una Macro

• Nombre: Debe ser único en todo el proyecto (los archivos pueden contener varias macros).
• Argumentos: Posicionales u opcionales con valor por defecto (tasa=4000).
• Cuerpo: SQL + lógica Jinja (if, for, set).
• return(): Opcional. Devuelve un objeto Python (lista, dict, número) en vez de texto.

{% macro nombre(arg1, arg2='default') %} {# lógica Jinja + SQL #} {% set x = arg1 ~ '_sufijo' %} SELECT {{ x }} {# o bien: {{ return(['a','b']) }} #} {% endmacro %}

3 Formas de Llamar una Macro

• {{ macro() }}: Imprime el resultado (SQL) en ese lugar del modelo.
• {% set v = macro() %}: Guarda el resultado en una variable (ideal con return()).
• {% do macro() %}: La ejecuta sin imprimir nada (ideal para run_query o acciones).

-- 1. Imprimir SQL SELECT {{ limpiar_texto('ciudad') }} AS ciudad -- 2. Guardar resultado {% set paises = obtener_valores(ref('dim_pais'), 'id') %} -- 3. Ejecutar sin imprimir {% do log('Procesando...', info=True) %}

¿De dónde salen? (Prioridad)

dbt busca macros en 3 lugares, en este orden de prioridad:

1. Tu proyecto (macros/) ➔ gana siempre.
2. Paquetes instalados con dbt deps (dbt_packages/dbt_utils/macros/).
3. dbt Core (macros internas como generate_schema_name).

Por eso puedes sobrescribir macros internas de dbt simplemente creando una con el mismo nombre en tu carpeta macros/.

mi_proyecto_analitica/ ├── macros/ │ ├── convertir_moneda.sql │ ├── generate_schema_name.sql ← override │ └── tests/valor_en_rango.sql ├── dbt_packages/dbt_utils/macros/ ← paquete └── dbt_project.yml

¿Qué es un Paquete? (dbt_utils)

Un paquete es un proyecto dbt de terceros lleno de macros ya escritas y probadas por la comunidad. Se declara en packages.yml y se descarga con dbt deps.

Sus macros se llaman con el prefijo del paquete: dbt_utils.nombre_macro(). Las más usadas: generate_surrogate_key, star, union_relations, date_spine, pivot.

-- Archivo: packages.yml packages: - package: dbt-labs/dbt_utils version: 1.1.1 -- Uso en models/fct_pedidos.sql SELECT {{ dbt_utils.generate_surrogate_key(['pedido_id','producto_id']) }} AS pedido_sk FROM {{ ref('stg_pedidos') }}

¿Qué es un Test Genérico? ({% test %})

Es una macro especial que define una regla de calidad reutilizable. dbt le inyecta automáticamente model y column_name desde el schema.yml.

Devuelve las filas que fallan: si el SELECT retorna 0 filas, el test pasa. Así es como están construidos por dentro unique y not_null.

-- Archivo: macros/tests/es_positivo.sql {% test es_positivo(model, column_name) %} SELECT * FROM {{ model }} WHERE {{ column_name }} <= 0 {% endtest %} -- Archivo: models/schema.yml - name: monto -- FLOAT tests: [es_positivo]

¿Qué es un Hook? (pre / post)

Un hook es SQL (normalmente una macro) que dbt ejecuta automáticamente antes o después de construir un modelo (pre_hook / post_hook) o al inicio / final de todo el dbt run (on-run-start / on-run-end).

Se usa para otorgar permisos, registrar auditoría o crear índices sin ensuciar el SELECT del modelo.

-- Archivo: models/fct_ventas.sql {{ config( materialized='table', post_hook="GRANT SELECT ON {{ this }} TO ROLE bi_reader" ) }} SELECT * FROM {{ ref('stg_ventas') }}

¿Qué es adapter.dispatch? (Multi-motor)

Es el mecanismo que permite que una misma macro tenga una versión distinta para cada motor (Postgres, Snowflake, BigQuery). dbt lee el type del target activo en profiles.yml y elige la versión con ese prefijo; si no existe, usa default__.

-- Archivo: macros/hoy.sql {% macro hoy() %} {{ return(adapter.dispatch('hoy')()) }} {% endmacro %} {% macro default__hoy() %}CURRENT_DATE{% endmacro %} {% macro bigquery__hoy() %}CURRENT_DATE('America/Bogota'){% endmacro %}

1.2 Demás Conceptos Fundamentales (Modelos, Materializaciones, Seeds, Sources, Tests, etc.)

¿Qué es un Modelo? (.sql)

Un modelo es simplemente un archivo de texto con extensión .sql guardado dentro de la carpeta models/ de tu computadora.

Contiene una única consulta SELECT. dbt se encarga de envolver ese SELECT dentro de un CREATE TABLE AS o CREATE VIEW AS en tu base de datos.

-- Archivo: models/stg_clientes.sql
SELECT
  id AS cliente_id, -- INT
  TRIM(full_name) AS nombre, -- VARCHAR
  status AS estado -- VARCHAR (Valores: activo, inactivo)
FROM prod_dw.raw_salesforce.sf_users
-- Ejemplo adicional uniendo source() y ref():
SELECT
  c.cliente_id,
  c.nombre,
  p.nombre_pais
FROM {{ source('crm', 'clientes') }} c
LEFT JOIN {{ ref('codigos_pais') }} p ON c.pais_id = p.id

¿Qué es una Materialización?

Es la forma física en que dbt guarda el resultado de tu modelo .sql dentro del Data Warehouse:

• View (Vista): Guarda solo la consulta virtual.
• Table (Tabla): Crea una tabla física completa cada vez.
• Incremental: Crea la tabla la primera vez y luego solo inserta filas nuevas.

-- Archivo: models/fct_ventas.sql
{{ config(materialized='table') }}

SELECT
  id_venta, -- INT
  monto, -- FLOAT
  fecha -- DATE
FROM raw_ventas

¿Qué es un Seed? (.csv)

Un seed es un archivo estático en formato .csv (como un catálogo de países, monedas o metas) guardado en la carpeta seeds/.

Al ejecutar dbt seed, dbt lee ese CSV de tu disco y crea una tabla real con sus datos dentro de la base de datos.

-- Archivo: seeds/codigos_pais.csv
id,nombre_pais,moneda
CO,Colombia,COP -- VARCHAR
MX,Mexico,MXN -- VARCHAR

¿Qué es un Source? (.yml + .sql)

Son las tablas crudas (raw) que ya existen en tu base de datos porque las cargó otra herramienta (Fivetran, Airbyte, Python).

Como dbt no las creó, debes declararlas en un archivo sources.yml especificando sus columnas, tipos de datos y reglas, para luego consultarlas mediante source().

-- Archivo: models/sources.yml
version: 2
sources:
  - name: crm # Alias del sistema
    tables:
      - name: clientes # Alias dbt
        identifier: sf_users # Tabla real
        columns:
          - name: id -- INT (Único)
          - name: status -- VARCHAR (Valores: activo, inactivo)
-- Uso en models/stg_clientes.sql
SELECT id, status FROM {{ source('crm', 'clientes') }}

¿Qué es ref()? (Función Jinja)

ref() es la función principal de dbt para conectar modelos entre sí. Toma el nombre de otro modelo o seed sin extensión y resuelve automáticamente su ruta física en el Data Warehouse.

Garantiza que dbt construya el DAG (linaje) ejecutando primero los modelos dependientes.

-- Archivo: models/dim_clientes.sql
SELECT
  c.cliente_id,
  c.nombre,
  p.nombre_pais -- VARCHAR
FROM {{ ref('stg_clientes') }} c
LEFT JOIN {{ ref('codigos_pais') }} p ON c.pais_id = p.id

¿Qué es un Test? (Prueba de Calidad)

Los tests en dbt son aserciones sobre tus datos para garantizar la calidad (ej. verificar que una columna sea única, no nula, o cumpla relaciones).

Se definen principalmente en archivos .yml adjuntos a tus modelos.

-- Archivo: models/schema.yml
version: 2
models:
  - name: dim_clientes
    columns:
      - name: cliente_id -- INT
        tests: [unique, not_null]
      - name: estado -- VARCHAR
        tests: [{accepted_values: {values: ['activo', 'inactivo']}}]

¿Qué es el DAG (Linaje)?

Es el mapa de dependencias que dbt arma automáticamente al leer tus source() y ref().

Si el modelo B tiene {{ ref('modelo_a') }}, dbt sabe que primero debe construir modelo_a en la base de datos antes de ejecutar modelo_b.

-- Orden de ejecución del DAG en consola:
1. source('crm', 'clientes') ➔
2. models/stg_clientes.sql ➔
3. seeds/codigos_pais.csv ➔
4. models/dim_clientes.sql

¿Qué es profiles.yml?

Es el archivo de configuración de conexión (fuera del repositorio del proyecto) donde defines a qué base de datos conectarte y en qué esquema trabajar.

Por ejemplo, define que en entorno dev escriba en dev_juan y en prod escriba en prod_dw.analytics.

-- Archivo: ~/.dbt/profiles.yml
mi_proyecto:
  target: dev -- Entorno activo
  outputs:
    dev:
      type: snowflake
      database: dev_dw -- VARCHAR
      schema: dev_juan -- VARCHAR

1.3 La Duda Clave: Si stg_clientes.sql es un archivo local, ¿por qué {{ ref('stg_clientes') }} consulta prod_dw.analytics.stg_clientes?

dbt nunca ejecuta consultas SQL contra archivos de texto en tu disco duro. dbt es un orquestador y compilador que trabaja siempre contra tu Data Warehouse (Snowflake, BigQuery, Postgres, etc.). El ciclo funciona en 3 pasos exactos:

Paso 1: Orden de ejecución Al ver {{ ref('stg_clientes') }} dentro de dim_clientes.sql, dbt detecta una dependencia y ejecuta primero el archivo models/stg_clientes.sql.
Paso 2: Creación en la BD dbt toma el SELECT de stg_clientes.sql y crea una tabla o vista real en tu Data Warehouse llamada prod_dw.analytics.stg_clientes (usando la base de datos y esquema configurados en tu profiles.yml).
Paso 3: Traducción del ref() Ahora que la tabla física ya existe en la BD, dbt reemplaza el texto {{ ref('stg_clientes') }} por la ruta real de esa tabla en la BD: prod_dw.analytics.stg_clientes.

¿Por qué ref(), source() y config() son macros? Porque funcionan exactamente como funciones

Todo lo que escribes entre {{ }} con paréntesis es una macro integrada (built-in) que dbt ya trae programada, sin que tengas que crearla en macros/. Se comportan como funciones de Python: tienen un nombre, reciben parámetros entre paréntesis (posicionales o por nombre, algunos opcionales con valor por defecto) y devuelven un valor que dbt pega en el SQL. Por eso ref('stg_clientes') no es "texto mágico": es una llamada a una función que recibe un parámetro y retorna la ruta real de la tabla.

Analogía en Python
# Así "piensa" dbt por dentro def ref(nombre_modelo): return f"{target.database}.{target.schema}.{nombre_modelo}"
Llamada en tu modelo .sql
SELECT * FROM {{ ref('stg_clientes') }} -- nombre parámetro
Valor devuelto (compilado)
SELECT * FROM prod_dw.analytics.stg_clientes
Macro vs. variable de contexto: las que llevan paréntesis (ref(), source(), var()) son macros/funciones porque reciben parámetros. Las que no llevan paréntesis (this, target, execute) son variables de contexto: objetos que dbt llena automáticamente y que solo lees. En la tabla siguiente se marcan ambas.

1.5 Ejemplos Detallados de Macros en dbt (Macro Definida ➔ Modelo .sql ➔ SQL Compilado en BD)

Las macros son la pieza más poderosa de dbt: te permiten escribir SQL una sola vez y reutilizarlo en cientos de modelos, adaptarlo a cada motor (Postgres, Snowflake, BigQuery), sobrescribir el comportamiento interno de dbt y automatizar tareas administrativas. Todo lo que ya usaste (ref(), source(), is_incremental()) es, por dentro, una macro.

La Duda Clave: ¿Una macro se ejecuta en la base de datos?

No. Una macro se ejecuta en tu computadora (Python/Jinja) durante la compilación. Su único trabajo es generar texto SQL. Lo que llega al Data Warehouse es el SQL ya resuelto, sin rastro de la macro. La única excepción es cuando la macro usa run_query(), que sí lanza una consulta real a la BD durante la compilación.

Paso 1: Parseo dbt lee todos los archivos de macros/, dbt_packages/ y las macros internas y las registra en memoria como funciones disponibles.
Paso 2: Renderizado Al compilar fct_ventas.sql, Jinja encuentra {{ convertir_moneda('monto') }}, ejecuta la macro con esos argumentos y obtiene el texto ROUND(monto / 4000, 2).
Paso 3: Envío a la BD dbt reemplaza la llamada por ese texto, envuelve el SELECT en su materialización (CREATE TABLE AS...) y lo envía al motor. Puedes verlo en target/compiled/.

convertir_moneda()
Macro básica con argumentos		 .SQL (MACRO)
macros/convertir_moneda.sql
  • Recibe el nombre de una columna como texto y devuelve una expresión SQL.
  • Los argumentos tasa y decimales tienen valores por defecto; puedes omitirlos o sobrescribirlos por nombre.
  • Se puede combinar con var() para que la tasa venga de dbt_project.yml.
Cuando la misma fórmula de negocio (conversión, redondeo, cálculo de margen) se repite en varios modelos. Cambias la macro una vez y se corrige en todo el proyecto.
1. Definición en macros/convertir_moneda.sql.SQL (MACRO)
{% macro convertir_moneda(columna, tasa=4000, decimales=2) %} ROUND({{ columna }} / {{ tasa }}, {{ decimales }}) {% endmacro %}
2. Variable global en dbt_project.yml.YML
vars: trm_eur: 4350
3. Uso en models/marts/fct_ventas_usd.sql.SQL
SELECT id_venta, monto_cop, {{ convertir_moneda('monto_cop') }} AS monto_usd, {{ convertir_moneda('monto_cop', tasa=var('trm_eur'), decimales=4) }} AS monto_eur FROM {{ ref('stg_ventas') }}
4. SQL real ejecutado en la BD (Postgres)COMPILADO
CREATE TABLE postgres_prod_dw.analytics.fct_ventas_usd AS ( SELECT id_venta, monto_cop, ROUND(monto_cop / 4000, 2) AS monto_usd, ROUND(monto_cop / 4350, 4) AS monto_eur FROM postgres_prod_dw.analytics.stg_ventas );

source() .YML
models/sources.yml
  • En un archivo .yml defines un alias de sistema (crm) y un alias de tabla (clientes).
  • Ese YAML actúa como un diccionario que mapea tus alias hacia la base de datos, el schema y el nombre físico real (identifier) de una tabla externa que ya existe en el Data Warehouse.
Exclusivamente en los primeros modelos (capa staging) para leer tablas crudas cargadas por herramientas externas (Fivetran, Airbyte, etc.).
1. Diccionario en models/sources.yml.YML
version: 2 sources: - name: crm # Alias del sistema (inventado por ti) database: prod_dw # Base de datos real en tu servidor schema: raw_salesforce # Esquema real donde cae la ingesta tables: - name: clientes # Alias de la tabla en dbt identifier: sf_users # Nombre físico real de la tabla
2. Modelo inicial models/stg_clientes.sql.SQL
SELECT id AS cliente_id, TRIM(full_name) AS nombre, country_code AS pais_id FROM {{ source('crm', 'clientes') }}
3. SQL real que dbt ejecuta en la BDCOMPILADO
SELECT id AS cliente_id, TRIM(full_name) AS nombre, country_code AS pais_id FROM prod_dw.raw_salesforce.sf_users
ref() .SQL
.CSV
  • No usa YAML. Toma el nombre exacto del archivo físico (.sql o .csv) sin su extensión.
  • Primero dbt materializa esos archivos como tablas/vistas reales en el esquema de destino configurado en profiles.yml (ej. prod_dw.analytics), y luego reemplaza ref() por esa ruta de base de datos.
En todos los modelos intermedios y finales (marts) para cruzar datos que ya pasaron por otro modelo o seed dentro de dbt.
1A. Archivo previo models/stg_clientes.sql.SQL

1B. Archivo previo seeds/codigos_pais.csv.CSV

2. Modelo final models/dim_clientes.sql.SQL
